# 팀 운영 핸드북

이 문서는 스타트업 팀의 지식이 사람의 기억이나 채팅 기록에만 남지 않도록 보관함을 운영하는 기본 규칙입니다.

## 기록 기준

- 회사 전략과 우선순위는 [[02 Company/Company Strategy|회사 전략]]과 OKR에 둡니다.
- 프로젝트 노트에는 결과, 성공 지표, 담당자, 상태, 다음 이정표를 둡니다.
- 회의 노트에는 목적, 참석자, 결정, 후속 작업을 기록하고 관련 프로젝트에 연결합니다.
- 중요한 선택은 별도 의사결정 기록으로 남기고 관련 프로젝트와 회의에서 연결합니다.
- 사용자 조사와 제품 발견 기록은 개인정보를 제거한 뒤 지식 영역에 보관합니다.
- 반복해서 참고할 수 있는 절차와 배운 점은 지식 문서로 정리합니다.
- 한 사실의 기준이 되는 문서는 하나만 두고, 나머지는 링크합니다.

## 업무 흐름

1. 새 정보를 [[01 Inbox/README|인박스]]에 기록합니다.
2. 프로젝트가 되면 [[08 Templates/Project Note|프로젝트 템플릿]]으로 노트를 만들고 `03 Projects/`에 둡니다.
3. 회의가 끝나면 [[08 Templates/Meeting Note|회의록 템플릿]]으로 결과를 기록합니다.
4. 장기적으로 영향을 주는 선택은 [[08 Templates/Decision Record|의사결정 템플릿]]으로 남깁니다.
5. 상태와 담당자를 Properties로 관리하고 `09 Bases/`에서 모아 봅니다.
6. 주간 검토에서 인박스와 활성 프로젝트의 다음 단계를 확인합니다.

## 상태 값

| 노트 종류 | 권장 상태 |
| --- | --- |
| 프로젝트 | `proposed`, `active`, `blocked`, `completed`, `archived` |
| 의사결정 | `proposed`, `accepted`, `rejected`, `superseded` |
| 지식 문서 | `draft`, `review`, `published`, `archived` |
| OKR | `draft`, `active`, `achieved`, `missed` |

## Properties 기준

`type`, `status`, `owner`, `team`, `project`, `date`, `review_date` 속성 이름을 일관되게 씁니다. 상태에는 위 표의 값을 사용하고, 담당자·프로젝트가 노트로 관리되는 경우 Properties에서 해당 노트를 내부 링크로 연결합니다.

## 실행 작업과 기록의 경계

Obsidian은 맥락, 회의 결과, 결정 이유, 참고 지식을 연결하는 곳입니다. 담당자와 마감일이 있는 실행 작업은 GitHub Issues, Linear 등 팀이 실제로 사용하는 작업 추적 도구에 두고 여기에는 해당 작업 링크와 배경을 남깁니다.

## 확장 플러그인

현재 보관함은 기본 플러그인만 사용합니다. Bases가 속성 기반 목록을 제공하므로 같은 역할의 데이터베이스 플러그인을 중복 설치할 필요가 없습니다. 반복 노트 생성을 자동화하고 싶을 때 QuickAdd, Obsidian 안에서 전체 작업 체크리스트를 조회하고 싶을 때 Tasks, 더 복잡한 동적 템플릿이 필요할 때 Templater를 검토합니다. 커뮤니티 플러그인은 파일과 네트워크에 접근할 수 있으므로 작성자와 코드, 공개 보안 점검 결과를 확인한 뒤 설치합니다.

## 접근과 공개

이 저장소는 공개 저장소입니다. 실제 회사의 미공개 전략, 고객·직원 정보, 계약, 자격 증명, 비공개 회의 기록은 여기에 넣지 않습니다. 팀 내부 지식에는 별도의 비공개 보관함과 접근 정책을 사용합니다.
